# 版本号规则

## 一句话

`versionName` = `主.次.补丁`（如 `1.10.0`）；`versionCode` 每次出包 **+1**，只增不减。

| 位 | 什么时候 +1 | 备注 |
|---|---|---|
| **主** | 不兼容的大改版 / 换底 | 至今没动过，仍是 `1` |
| **次** | **新增模块** or **新增一块用户能看见的功能区** | 提「次」时补丁归零 |
| **补丁** | 其余每次出包：修 bug、既有功能的小改进、文案调整 | 就是「这一轮出了几个包」 |

## ⚠️ `versionCode` 与 `versionName` 无关，别去推导

`versionCode` 是**独立自增计数器**（现在是 80），**不要**按 `1.9.54 → 10954` 那样算。

理由：**在线检查更新只比 `versionCode`**（`UpdateDialog` 用 `minVersionCode` 判强制更新，
`versionName` 只是显示给人看）。它唯一要满足的性质是**单调递增**：

- 一旦改成「由 versionName 推导」⇒ 某次忘了改 versionName 就会导致 code 不增，
  老用户**永远收不到更新**，而界面上看不出任何异常
- **倒流的 code 是不可逆的事故**（装了高的就装不回低的）

## ⚠️ 已知偏差（2026-10-12 盘点）

`1.9` 这一个「次」号下压了 **54 个补丁版**，其中**至少两次按规则该提「次」**：

- **v1.9.44** 新增了 `features:nfc` 模块（校园卡）⇒ 本应是 `1.10.0`
- **v1.6.8** 新增了 `features:notify` 模块（通知与提醒中心）⇒ 同理

⇒ **结论：规则本身没错，是执行漏了。** 不是「1.9 有什么特殊」，就是没人在出包时回头看这一条。

## 执行动作

1. **本次**：`v1.9.54` 之后的第一个正式版定 **`1.10.0`**，把「自习推荐 + 认证收敛」
   作为 1.9 系列（校园数据接入这一大轮）的收尾。
2. **往后**：出包前扫一眼这一版有没有**新模块 / 新功能区**——有就提「次」。
3. **tag 要跟上**：`v1.9.32`（09-30）之后就没再打过 tag。tag 是「哪一版真的出过包」
   的凭据（记忆里那条「本地 tag ≠ 已推送」就是为这个）。
   ⇒ 每次出包 `git tag v<versionName>`，并**单独** `git push origin v<versionName>`。
