# NFC 校园卡只读探测 —— 真卡实测记录与协议规则

> 对象：北理工校园卡（UID `7775F07B`）。设备：一台带 NFC 的安卓机（开发机 ZTE NP05J 无 NFC 硬件）。
> 结论全部来自**用户贴卡三次**拿回的 dump，不是推测。推测的地方都标了「（推测）」。

## 0. 红线（改代码前先读这一段）

1. **只读**。模块内不存在任何写命令的构造入口：没有 `writeBlock`、没有 `UPDATE BINARY`、
   没有改密钥、没有增值减值。新增任何命令前先自问「发出去卡还能不能恢复原样」，答不上就别加。
2. **允许清单**而不是黑名单：`CardProbeLogic.READ_ONLY_INS` 只放 `A4 B0 B2 C0 CA 84`，
   且 CLA 必须是基本通道（0~3）。最后一道闸门在唯一碰 `transceive` 的 `NfcController.send()` 里。
3. **⚠️⚠️ 带 MIFARE Classic 兼容层的卡绝对不许写 NDEF**。
   校园卡 techList 里有 `NdefFormatable`（字面意思「可以当标签用」），
   但对 Classic 写 NDEF / `format()` 会重写**扇区尾块**（密钥 A/B + 存取位），
   我们没有厂商密钥，**无法恢复**。`writeShortcut()` 见到 Classic tech 直接拒绝。
4. **认证失败就停**，不去破密钥（不跑嵌套认证攻击）。那既是在撬别人的锁，也几乎肯定徒劳。

## 1. 这张卡是什么

```
techList: IsoDep, NfcA, NfcA, MifareClassic, NdefFormatable
```

- **双界面卡**：既有 ISO 14443-4 / ISO 7816-4 通道，也有 MIFARE Classic 兼容层。
- ⚠️ **判类型时 `IsoDep` 必须排在 `MifareClassic` 前面**。反过来会判成
  「MIFARE Classic，读扇区要密钥」⇒ 上层直接放弃 ⇒ **唯一能安全取数的 APDU 通道被自己掐掉**。
  这个 bug 真发生过：第一次贴卡拿到的 APDU 数是 **0**。
- `techList` 里 `NfcA` 会**重复出现**（部分 ROM 的枚举行为），展示时要 `.distinct()`。

## 2. Classic 层：空的

```
扇区 0..15 · 全部用 FFFFFFFFFFFF KeyA 认证通过
  块 0: 77 75 F0 7B 89 28 04 00 90 10 15 01 00 00 00 00
  其余块: 全零
```

- 块 0 是标准制造商块：`77 75 F0 7B` = UID，`89` = BCC（UID 四字节异或，自校验通过），
  `28` = SAK，`04 00` = ATQA。
- **除 UID 块外全是零 ⇒ 学号不在 Classic 区**。这条路到此为止，
  **不要再试别的密钥**（换密钥只会重复同一个结论）。
- 顺带：`FFFFFFFFFFFF` 全通说明这张卡的 Classic 层是**出厂状态没被动过**，
  真正的一卡通数据全在 CPU 卡那侧。

## 3. APDU 层：数据全在 FID 盲扫里

### 3.1 走不通的两条路

| 尝试 | 结果 | 为什么 |
|---|---|---|
| `SELECT MF 3F00` | `9000` | FCI 里 `84` = `1PAY.SYS.DDF01` —— **MF 借用了接触式支付目录的名字** |
| `SELECT PSE 1PAY.SYS.DDF01` | `9000`，FCI 与 SELECT MF **完全相同** | 卡厂把 MF 的 FCI 直接填成了 PSE 的，`84` 不是真目录名 |
| `READ RECORD SFI=1 记录 1/2/3` | `6A82` ×3 | MF 下没有 SFI=1 的文件 |
| `SELECT PPSE 2PAY.SYS.DDF01` | `6A82` | 非接触式支付目录不存在 |
| `READ BINARY SFI=1..30` | `6A82` ×30 | **不选中文件就 READ BINARY** = 闭着眼敲门 |

⚠️ 结论：**AID / 支付目录这条线对国内校园卡没用**。MF 那个 `1PAY.SYS.DDF01`
只是个名字，卡里没有 EMV 那种目录结构。

### 3.2 唯一有效的路：`SELECT by FID` 盲扫

`00 A4 02 00 02 <FID hi> <FID lo>` + 命中后 `READ BINARY`。
默认区间 `0001~00FF`（业务文件都在低区）。实测命中：

| FID | 现象 | 解读 |
|---|---|---|
| `0011` `0012` `0013` | `9000` + `READ` 全零 32 字节，续读 `6B00` | 存在但空（长度 32 字节，内容全零） |
| `0010` | `9000`，FCI 是**目录**结构；`READ` 回 `6986` | **是 DF 不是 EF** ⇒ 见 §3.3，要进去再扫一层 |
| `0015` | `9000`，`READ` 回 **`6C1E`** → 按 30 字节重发得到 30 字节 | 见下方「0015 里是什么」 |
| `0016` | `9000`，`READ` → `00 00 B8 DF CC EC CF E8 00 00 …` | **GBK = 姓名「高天翔」** ⇒ 卡里确有身份信息 |
| `0018` | `9000`，`READ` 回 **`6981`** | **定长记录文件**，不吃 READ BINARY，要改 READ RECORD |
| `001A` `001B` | `9000` + `READ` 全零 | 存在但空 |
| `0001~000F`、`0019`、`001C~0020+` | `6A82` | 不存在 |

### 0015 里是什么（30 字节，已读到）

```
00 ×17  |  44 54 38 00 00 00 00 20 28 08 30 00 02
              "DT8"            └─ BCD 2028-08-30 ─┘
```

- `44 54 38` = ASCII **"DT8"**（含义未证实，**别猜**）。
- `20 28 08 30` 按 BCD 读是 **2028-08-30**。用户学号 `1120241355` ⇒ **2024 级**，
  本科 2024 级正好 2028 年毕业 ⇒ 「**卡有效期**」这个解释与事实自洽（**是推论，不是结论**）。
- ⚠️ **这个文件里没有学号**（既没有 BCD `11 20 24 13 55`，也没有 ASCII `1120241355`）。

### 其余文件都是空的

`0011 0012 0013 001A 001B` 首次 `READ` 回 `9000` + 32 字节全零，续读 offset=`0x20`
一律回 `6B00`（偏移量超界）⇒ 文件长度就是 32 字节且内容全零。
`0015` 续读同样回 `6B00` ⇒ 佐证它就是 30 字节（与 `6C1E` 完全对得上）。

⚠️ `6B00` **不是故障**：它正是「你要的偏移量已越过文件末尾」的答复，
在「沿文件往下读」时它就等于「这个文件到这里就没了」。

## 3.3 目录（DF）：`0010` 得进去再扫一层

`SELECT 0010` 的 FCI：`6F 18 84 10 D1560001018003800000010000100 2 A5 04 9F 08 01 02`

- `6F` 底下挂 **`84`（16 字节 DF 名）** 和 `A5`（其中 `9F08`=02，应用版本）——
  这是**目录（DF）的 FCI 结构**；普通文件的 FCI 里是 `80`（长度）`82`（存取条件）
  `83`（文件标识）那一套。
- 所以 `READ 0010` 回 **`6986`**（当前文件不允许该命令）是**正确行为**：
  目录不是文件，不能直接读，它的内容在**它自己那一层**。
- 处置：重新 SELECT 它，进去之后按 **SFI** 扫（EMV 的一贯做法），
  再扫一小段 FID 兜底。最多进 2 个目录 —— 用户贴在手机上不动的那几秒是有限的。

## 4. 三条必须自动跟的协议规则

这三条都是「卡在说『话还没说完 / 你命令用错了』」，**不是失败**。
把它们当错误处理，表现出来就是「这卡读不出来」，而数据其实就在那儿。我们**一次全丢过**。

### 4.1 `6C xx` —— Le 写错了

- 含义：正确的 Le 是 `xx`。`xx = 00` 按规范代表 **256**，不是 0。
- 处置：**原样重发同一条命令，只把最后一个字节换成 `xx`**。
- ⚠️ 只允许对**读指令**（INS ∈ `B0 B2 C0`）做。因为「末尾是 Le」这个前提不是所有命令都成立 ——
  比如 `SELECT by FID` 的 `00 A4 02 00 02 00 10`，末尾那个 `10` 是文件号的一部分，
  换掉它就变成去选另一个文件了。`CardProbeLogic.withLe()` 对非读指令直接抛异常。
- 实测：`READ 文件 0015` 回 `6C1E` ⇒ 按 30 字节重发才拿到内容。

### 4.2 `61 xx` —— 数据还有，要再问一次

- 含义：还有 `xx` 字节等着取。`xx = 00` 同样是 256。
- 处置：发 `GET RESPONSE`：`00 C0 00 00 <xx>`。

### 4.3 `6981` / `6986` —— 命令用错了，不是文件不存在

- `6981` = 命令与文件结构不兼容（定长记录文件不吃 READ BINARY）。
- `6986` = 当前文件不允许这条命令（**选中的多半是目录不是文件**）。
- 处置：改发 `READ RECORD`（**当前 EF**）：`00 B2 <记录号> 04 <Le>`。
  ⚠️ P2 = `0x04` 与按 SFI 的 `(SFI << 3) | 0x04` 是**两条不同的命令**，别搞混。
- 实测：`0018` 文件正是这一种；`0010`（DF）也会回 `6986`，属预期。
- ⚠️⚠️ **回退的判断依据必须是「读命令」的结果，不是 SELECT 的结果**。
  这个 bug 真发生过：第一版把回退挂在 SELECT 的返回上，而 SELECT 回的是 `9000`，
  回 `6981` 的是紧接着的 READ ⇒ **回退永远不触发，0018 被整片漏掉**。
  真卡 dump 里能看到证据：`[SELECT 文件 0018] -> 9000` 之后只有
  `[READ 文件 0018 前 32 字节] -> 6981`，中间**没有**任何「改读记录」的行。

**`6981` 与 `6986` 要分开处理**：前者是定长记录文件（改 `READ RECORD` 就好），
后者是目录（要进去再扫一层，见 §3.3）。混成一个就会出现「对目录发 READ RECORD」
这种白费力气的事。

## 5. 编码规则

- **中文一律 GBK**。`B8 DF CC EC CF E8` → 「高天翔」；用 UTF-8 解只会是乱码。
  GBK 是 ASCII 超集，所以英文也走同一条路，不用分两遍。
- 判据：解出来**不能有替换字符（U+FFFD）、不能有控制字节（< 0x20）**。
  随便一段二进制硬解 GBK 也会出字符，所以不满足就返回 `null`（UI 只显示十六进制），
  **宁可给 null 也不端一坨乱码给用户**。
- 读取时先去掉首尾的 `0x00` 填充 —— 文件里的空位都是零。

## 6. UID → 卡面印刷号：不猜，列候选

实测 `7775F07B`：

| 候选 | 值 |
|---|---|
| 正序当整数（十进制） | `2004217979` |
| 反序当整数（十进制） | `2079356279` |
| 正序十六进制 | `7775F07B` |
| 反序十六进制 | `7BF07577` |
| 正序十进制拼接（每字节补 3 位） | `119117240123` |
| 反序十进制拼接 | `123240117119` |

⚠️ 换算规则**各校自定、没有标准**。所以全列出来让用户对着卡面认，
**不由我们挑一个冒充结论**。用户报的卡面号尚未与任一项对上（未证实）。

- **待读**：`0018`（记录文件，本轮修好回退后才能读）、`0010` 目录内部。

## 8. 贴卡一次的成本很高 ⇒ 能自动跟的一律自动跟

一次扫描就是用户把卡贴在手机背面不动几秒。所以：

- 返回里挖到 `4F`（ADF 名）就**自动跟着 SELECT**（最多 3 个）。
- `6Cxx` / `61xx` 自动补发（最多三轮防呆）。
- 命中文件后**沿文件连读三段**（offset `0 / 0x20 / 0x40`）——
  前 32 字节是零**不等于**文件是空的。
- 慢的一轮（FID 盲扫，约 400 条命令）放在开关后面，**中途掉卡保留已拿到的部分**；
  三轮（APDU 基础 → Classic 扇区 → FID 深扫）**各自吞掉自己的异常**，前面拿到的不被后面拖垮。

## 9. UI 纪律

- **三个区块永远渲染**，哪怕是「本设备不支持 NFC」的机器 —— 只是把原因说清楚。
  （本项目踩过三次「有数据才渲染」的坑，见长期记忆第 0.7 条。）
- 一次扫描会有三四百条记录，默认**只列拿到数据的**，但**如实标出总条数**并提供一键展开 ——
  这既不藏信息，也不把用户埋掉。
- 事实与推论分开写。「卡面号候选」「默认密钥都没通过」这种措辞是有意的：
  **别把推论写成结论**。
