## 一、批次 A：出分链路收口（最高优先，已有代码但半通）

**为什么排第一**：出分提醒的解析、worker、渠道、去重**全都写好了**，只有两个断点让它「可能永不触发 / 点了跳错地方」。修完就能宣称五类提醒全部可用。

### A1 ✅ 已完成（v1.9.8，真机验证通过）
- **做法**：新增**无参**顶层路由 `score` —— 常量放 `:config` 的 `AppRoutes.SCORE`（`features:notify`
  够不着 `:features`，与组件跳登录同一套路）；`NavDestConfig.Score` + `composableScore` +
  `MainApp` 注册；通知 route 由 `PageShowOnNav.BIT101Web` 改为 `AppRoutes.SCORE`。
- ⚠️ **必须无参**：`MainApp` 兜底是精确匹配，`web/{url}` 那类参数化路由匹配不上（跳错页的根因）。
- **验收**：`adb shell am start -n cn.bit101.android/.features.MainActivity --es bit101_goto "score"`
  → 真机截图确认落在**成绩查询页**（学号密码已自动填入，点「查询」即出成绩）。不必等真出分。

### A2 ✅ 已完成（v1.9.9，真机实测已同步 50 门课）
- **`GET /scores` 恒 404**（上游 BIT101-Android 亦然）→ 出分提醒**从未触发过**（不是解析问题）。
- **新链路已接上**（逆向网页版得到的契约）：`POST login.bit101.flwfdd.xyz/api/jwb/bit101/score
  {username,password}` → `202` challenge_id + access_token → `GET /api/auth/{id}`
  （头 `X-Challenge-Token`）轮询到 `ready_services` 含 `jwb` → 带 `Authorization: Bearer`
  再请求原路径；`data` 是「第 0 行表头」的二维数组 —— **正好喂给现有 `ScoreLogic`**。
- ⚠️ **12h 限频必须有**：每次检查 = 一次学校统一身份认证登录，而触发点是「App 启动 + 每日任务」，
  不限频必撞风控（昨晚实测短时间多次登录 → `waiting_sms`；今早冷却后再试即通过）。
- ⚠️ **顺带修掉一个真 bug**：真实表头里 `课程编号` 在 `课程名称` 之前，原实现
  `contains("课程")` 取第一个 → 会把 `09000410` 当课名。已改「关键词优先级 + 排除词」并用真实表头锁进单测。
- **可见性**：设置 → 提醒 显示「最近检查：MM-dd HH:mm · 已同步 N 门课 / 学校要求短信验证，已暂停 /
  获取失败 / 未登录」+ **「立即检查一次」**按钮（跳过限频）。

## 三、批次 C：一卡通流水（阻塞，需用户配合）

- **现状（已查实）**：`/myaccount/openMyAccount` → 302 到卡务系统**充值**登录页；该页只有「学工号 + 金额 + 支付方式」，其 JS 只调充值/建单接口（`temporaryUserBind` 等，**涉及真实付款，不碰**）；其它候选路径全部 302 errorPage；i北理走钉钉免登，Web 端无等价入口。
- ⚠️ **更正（2026-09-26 复核）**：`cardpay/openCardRechargeLogin` 页面**只有「学工号 ×2 + 充值金额 + 支付方式」，
  没有任何密码输入框** —— 所以「卡务查询密码」这条路在 Web 端并不存在（此前判断有误）。
  该页文本只有「校园卡充值 / 使用说明 / 充值上限 200 元」。
- ⛔ **最终结论（2026-09-26，探针带 CAS 会话实测）：流水是钉钉专属，App 端拿不到**
  1. 服务端**按 UA 分模板**：移动 UA 抓到的是「校园移动服务平台」（余额 + 个人中心 + 6 个功能按钮），
     桌面 UA 是另一套模板 —— 用户截图那个页面就是移动模板。
  2. 移动版「查询流水」的 href 是 `/myaccount/openMyAccount?openid=...`，**带会话仍 302 到
     `cardpay/openCardRechargeLogin`**（该页只有学工号×2 + 充值金额 + 支付方式，无查询入口、无密码框）。
  3. 6 个功能按钮由 `GET /home/queryUserFunciton` 下发，而它直接回
     `{"message":"请使用钉钉客户端访问","success":false}` —— 非钉钉容器**拿不到菜单**，
     也就拿不到流水的真实入口（POST 变体分别 302 到 errorPage / 充值页）。
- **⇒ 一卡通流水只能在 i北理（钉钉）里看，本项目不再尝试**（技术 + 权限双重限制）。
  结论与复现步骤已写进 `api/src/probe/.../CampusCardProbe.kt` 文件头，日后学校若开放 Web 端查询，
  用该探针重跑第 2 步即可验证。
- **替代方案 → ✅ 已实施（v1.9.11）**：App 侧只记录**余额变化趋势**（每次取到余额时本地留一条采样），
  详情页原生展示「今日 / 近 N 天」余额变化。数据不出设备、不依赖流水接口。
  实现与口径见 `data/school/CampusCardBalanceLogic`（18 条单测）与本文档第十节。
- **拿到后**：原生流水列表页（分页 + 月度汇总），复用 `CampusServiceScreen` 的卡片组件。
- **本批次不做任何投机性实现**（不碰支付相关接口）。

### F1 空教室：校区 → 教学楼 → 教室（三级折叠）

- **改动**：`FreeClassroomSearchViewModel` 改为一次拉**全部校区**的教学楼
  （`getBuildingInfos()` 不带 `campusCode` —— SDK 此时**不加校区过滤参数**，服务端返回所有校区的楼，

  按校区分组；UI 新增 `CampusItem` 作为最外层。
- **默认校区**：设置里的「当前校区」改名「**默认校区**」—— 只决定「谁排最前 + 进来自动展开」。
- ⚠️ **降级路径**：拉全部若返回空或抛错，自动退回 `getBuildingInfos(默认校区)`，即**改版前的老行为**；
  连默认校区都没设过才如实报「拉取失败」。
- ⚠️ **配色**：校区层用中性 `surfaceContainerHigh`，刻意避开 PrimaryContainer（与右下角 FAB 糊）
  与 SecondaryContainer（与教室卡片糊）—— 这是原实现用注释记下来的坑。
- **验收**：真机 → 卷 → 空教室 → 应看到多个校区（默认校区在最上且已展开）→ 点教学楼展开出教室。

### F2 一卡通余额趋势

- 每次成功取到余额记一条采样到 `filesDir/campus_card_balance_history`（纯文本 `时刻|金额`）。
- 详情页 `余额变化` 行：`今日 -¥5.95 · 近 7 天 -¥25.95`（正数=充值、负数=消费）。
- **口径（诚实优先）**：今天只采到一次 → 不给「今日变化」（不编数）；历史不足 7 天 → 写「近 3 天」；
  7 天窗口内没有采样 → 只报今日；一条历史都没有 → 「记录中（攒够历史后显示变化）」而不是整行消失。
- **合并**：同一天、金额未变的连续采样只留**最早**那条（余额大多时候不变，不合并会把文件撑大）。
- ⚠️ 文件读写在 `Dispatchers.IO`，且只在「已登录 + 解析出金额」时记录（未登录页面上那几个数字来自登录页）。

### F3 两处小修

- **组件点课表条目 → 课表 tab**：`WidgetLine.openTab` 为 null 时 `GotoRequest.Focus` 会被
  `takeIf` 判成无附加信息丢掉 → `TabPager` 的 `requestedPage = null` 就不切页；
  App 已停在课表页的 DDL / 动态 tab 上时点课程行会「毫无反应」。课程行与空闲行现在都显式带
  `ScheduleTabs.COURSE`（空闲行也一并变可点）。
- **详情页余额补 `¥`**：服务端给的是裸数字（`34.05`）。
